1. The 30-second pitch

"Our developers use different AI agents: Claude Code, Cursor, Copilot. None of them have API keys, so a classic RAG review bot isn't possible. This tool gives the whole team one review standard. One procedure file and a wiki of team rules live in the repo, every agent follows them, and CI runs the same review on every PR. The LLM proposes findings and a deterministic layer checks them. That means no hallucinated line numbers, no made-up rules, and only rule-backed blockers can stop a merge."

Three ideas to get across

IdeaOne-line explanation
Works with any agent.ai-review/REVIEW.md is the single source of truth. The Claude, Cursor, Copilot and AGENTS.md files are 5-line pointers to it.
A wiki instead of RAGThe team writes rules as markdown pages. A routing table maps file paths to the pages that apply. The agent reads only those pages. It's deterministic and explainable, and it needs no embeddings or API.
The LLM is an untrusted proposerEvery finding must cite a real rule and point at a line the PR actually changed. Anything else is dropped, and the report lists what was dropped and why.

Who uses it

  • Author, before pushing: /ai-review in their own agent. This is where most of the value is, because problems get fixed before a human ever sees them.
  • CI, on every PR: posts one PR comment and keeps it updated, then gates on blockers.
  • Human reviewer: reads a ranked list and can spend their attention on design.
  • Tech lead / owners: maintain the wiki. That is how the reviewer improves over time.

What it checks

  • Tools (no LLM): committed secrets, PR template filled, a rollback plan for migrations, tests changed, PR size.
  • LLM, grounded in the wiki: authz/IDOR, injection, PII in logs, swallowed errors, async pitfalls, destructive migrations, missing negative tests, team conventions, past-incident pitfalls, whether the description matches the diff, prompt injection.

screen Two framing lines.

2Spot the bugs yourself

screen invoices.ts lines 13–26 and the new app.use("/invoices", …).
say "Take 20 seconds. How many problems do you see?" (Usually people find 2–3. The PR has more than 12.)
land Humans miss things in a skim. This motivates the tool without blaming anyone.

3The kit in the repo

screen .ai-review/ (REVIEW.md, wiki, configs) and the adapters: .claude/commands, .cursor/rules, AGENTS.md, Copilot prompt, CI workflow.
say "One command, aireview install, drops this in. Look at the Claude command: it only says 'follow REVIEW.md'. Every agent gets the same procedure."
land A single source of truth. Changing the process means editing one file.

4The wiki

screen Rule SEC-002 (ID, severity, Why, Bad/Good examples) and the routing table. wiki-lint reports 28 rules and 0 errors.
say "These are our rules in plain markdown: code review comments turned into documentation. The routing table says which pages apply to which paths. It's linted like code."
land The team owns the reviewer's knowledge. Delete a rule and the check is off; write a rule and it's on.

5Routing

screen aireview route … lists each page and the file that caused it to be read.
say "For this diff, the agent reads 9 pages, and we can see why: authz.md because of src/routes/**, migrations.md because of the SQL file."
land This replaces RAG. It's deterministic, explainable, and costs nothing.

6Deterministic checks

screen 6 tool findings: the Stripe key (blocker), no tests, no rollback plan, PR template placeholders, an unticked checkbox, no ticket.
say "Before any LLM runs, cheap code checks run. They're repeatable and give the same answer every time. We never pay an LLM to do what a regex can."
land Tools first, LLM for judgment calls.

7The context bundle

screen The bundle's section headings. Above === UNTRUSTED INPUT ===: procedure, schema, tool results, wiki pages. Below it: PR text and diff.
say "Everything the agent needs is in one file. PR text and code are marked as data, never instructions. That matters because this PR's description hides an 'ignore previous instructions' comment."
land Prompt-injection defense is part of the design.

8LLM review

screen Mock: the "model" proposes 24 findings. With --live, real Claude Code runs headless with read-only tools (about 1–2 minutes).
say "In CI this is claude -p with Read/Grep/Glob only: no shell, no edits, no network. Locally, it's whatever agent the dev already uses. For the demo I use a recorded response that includes typical model mistakes."
land Same procedure locally and in CI. The runner can be swapped.

9Validation (the key moment)

screen 22 kept, 8 dropped. The dropped ones: a hallucinated line 88, unknown rule SEC-999, a file not in the diff, confidence 0.35, a suppression with a reason, duplicates, a schema error. A blocker without a rule gets downgraded.
say "This is what makes it trustworthy. The model is a proposer. Every finding must cite a real rule and point at a changed line. Everything dropped is listed, nothing is hidden."
land Trust comes from verification, not from the model.

10Report and gate

screen "❌ Changes requested", 5 blockers, and exit code 1.
say "This exact markdown is the PR comment. Only blockers backed by a wiki rule can fail the build. Teams start in advisory mode and switch to gating once they trust it."
land Gating is narrow and opt-in.

11Human override

screen The same findings with label ai-review-override give exit code 0 and a warning.
say "The tool advises and people decide. An override is a visible, auditable label, not a hidden bypass."
land Humans stay accountable.

12In the dev's own agent

screen cd <demo repo> && claude → /ai-review main (optional live).
say "A dev types /ai-review. The agent runs aireview context, reviews, writes findings.json, and runs aireview validate. Same report as CI, before anyone else sees the code."
land Most of the value comes before the PR exists.
Live-run result to quote: real Claude Code on this PR found every seeded issue (5 blockers, 11 major), had 0 findings dropped by validation, and flagged the prompt-injection comment on its own. The sample is in demo/sample_reports/live_claude_report.md.

4. Concepts to explain if asked to go deeper

ConceptExplanation
Single source of truthAll behavior lives in REVIEW.md (procedure, review passes, verification step, JSON schema, severity rubric). Adapters stay thin, and a test enforces that they're under 30 lines and reference REVIEW.md. Without the CLI, REVIEW.md has fallback steps (plain git diff, manual routing), so it still works in any agent.
Wiki rule format### SEC-002: title + **Severity:** + **Why:** + Bad/Good code. The rule's severity is the default for its findings. wiki-lint checks IDs are unique, severities are valid, Why is present, examples exist, and every page is reachable from the index.
Validation rulesEach finding goes through these checks: schema, then rule exists (or general), then file is in the diff, then line is inside a changed hunk, then confidence ≥ 0.6, then no review-ignore RULE: reason comment (reason mandatory), then dedupe (tool beats LLM), then the cap of 15, which trims nits first and never drops blockers.
Gateadvisory always exits 0. blocker exits 1 if there's a rule-backed blocker, unless the PR has the override label. general findings can never block; to enforce one, write a rule for it.
CI hardeningTriggers on pull_request (not _target). Fork PRs are skipped, so there are no secrets on untrusted code. contents: read only. PR text is never interpolated into the shell script. Claude gets only Read/Grep/Glob. The API key exists only in CI.
Suppressions// review-ignore CONV-003: boot banner, removed in PAY-530. Each suppression applies to one rule on one line, and needs a reason so it's a decision, not a mute button.

5. Likely questions and answers

QuestionAnswer
Why not RAG?Devs have no API access, and IDE agents can already read files. Routing by path is deterministic and explainable, and a team wiki is a few dozen pages, not millions of documents. If it grows to hundreds of pages, split it per service and keep shared security pages always routed.
What about hallucinations?Validation drops anything not tied to a real rule and a changed line, and lists what it dropped. In the live run, 0 findings were dropped, but the safety net exists for runs where the model gets things wrong.
It's nondeterministic. Can it gate merges?Only rule-backed blockers gate. Deterministic checks catch the most critical items (like secrets) without an LLM. Start in advisory mode, measure, then gate. There's always a label override.
What if devs skip the local review?CI runs the same review anyway. The PR template has a "ran /ai-review" checkbox. Local review is about speed for the dev, not enforcement.
How does the wiki stay current?When a finding is disputed and the dev is right, the agent proposes a wiki edit (REVIEW.md "After the review"). Every incident adds a PIT-* rule. Wiki edits go through normal PR review and lint.
Cost?One headless run per PR push, and routing keeps the context small. Deterministic checks are free. Concurrency settings cancel stale runs.
Large PRs or monorepos?The diff has a size budget, and truncated files are listed in the report. PR-005 flags oversized PRs. For monorepos, add routing rows per package, or keep one wiki per service plus a shared core.
Doesn't this replace SAST and linters?No. Keep semgrep, gitleaks, eslint and npm audit as their own CI steps. REVIEW.md tells the agent not to repeat what tools already catch. This covers what they can't: authz logic, migration risk, whether tests are meaningful.
Why Python for the CLI?Standard library only, so nothing to install beyond Python, and it's easy to read. It's language-agnostic about the code under review; the demo service is TypeScript.
How do we know it's working?Track the share of findings acted on versus dismissed, overrides per week, escaped defects that map to an existing rule, and time to first review.

6. Before you present: checklist

  • Run cd ~/work/git/personal_code/agents/ai_assisted_code_reviewer && demo/present.sh --auto once as a rehearsal. It should end at STEP 12 with gate exit code 1.
  • Use mock mode for the talk: offline and predictable. Use --live only if there's network and time (about 1–2 minutes of waiting in step 8). Have demo/sample_reports/live_claude_report.md open as a backup.
  • Use a large terminal font and a dark theme. Clear the screen before you start.
  • Optional finale: export PATH="$PWD/.venv/bin:$PATH"; cd $TMPDIR/aireview-present && claude → /ai-review main.
  • If something breaks: .venv/bin/pytest (140 tests, about 3 seconds) proves the pipeline, and the sample reports show the output.

8. Command cheat sheet

aireview install [--only claude,cursor,agents,copilot,ci] [--force]   # add the kit to a repo
aireview wiki-lint [--strict]                                          # check rules + routing
aireview route <paths…>                                                # which wiki pages apply
aireview checks   --base origin/main                                   # deterministic only
aireview context  --base origin/main [--include-uncommitted]           # bundle for an agent
aireview validate --base origin/main [--findings f.json]               # agent findings → report
aireview run --runner claude|mock --base origin/main [--labels x]      # full pipeline (CI)

demo/present.sh [--live|--auto]     # presenter walkthrough (this guide)
demo/run_demo.sh [--live|--setup]   # quick end-to-end demo

9. The project in 4 lines

1. A code-review tool that every AI agent can run (Claude Code, Cursor, Copilot, Codex) and that CI runs on every PR, with no developer API keys.
2. It's grounded in a team-owned markdown wiki of rule-ID'd guidance, routed by file path instead of RAG, and driven by one procedure file (REVIEW.md).
3. Deterministic checks run first (secrets, PR template, tests, size). The LLM proposes findings, and a validation layer drops anything not tied to a real rule and a changed line.
4. The output is a ranked PR report with a narrow, overridable merge gate. The stdlib Python CLI has 140 tests and a TypeScript demo that Claude Code reviewed live, catching every seeded issue.
